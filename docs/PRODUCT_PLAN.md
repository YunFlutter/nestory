# Nestory MVP 기획

Nestory는 물건을 어디에 넣었는지 사진과 위치 관계로 기록하는 개인용 보관 앱이다. 홈에서 물건 목록보다 공간을 먼저 보여주고, 사용자가 공간과 보관함을 따라 탐색하거나 기억하는 이름으로 검색해 물건의 위치를 확인하게 한다.

이 문서는 사용자와 합의한 첫 버전의 개발 기준이다. 현재 앱은 Flutter 카운터 템플릿이며 아래 기능은 아직 구현되지 않았다. 개발 절차는 [공통 개발 지침](../AGENTS.md)을 따른다.

## 1. 목표와 개발 범위

- 1인이 Flutter와 Firebase로 개발하고 운영할 수 있는 개인용 MVP를 만든다.
- Android와 iPhone을 첫 출시 범위에 함께 포함한다. 양쪽에서 같은 등록·검색·이동 흐름을 제공한다.
- iOS는 최소 18.0을 기획 기준으로 하고 27.0까지 호환성을 검증한다. 현재 저장소 설정은 15.0이며 설정 변경과 호환성 검증은 별도 구현 작업이다.
- iPad 전용 화면, Web과 데스크톱 제품은 첫 버전에서 제외한다. 생성된 플랫폼 폴더가 있다는 이유로 지원 범위를 확대하지 않는다.
- 앱은 사용자가 기록한 위치를 보여준다. 실제 물건 이동을 자동 감지하지 않으므로 이동 수정이 쉬워야 한다.

핵심 성공 조건은 등록이 빠르고, 저장한 물건의 현재 위치를 쉽게 찾으며, 보관함을 옮겨도 내용물의 경로가 정확하게 따라 바뀌는 것이다.

## 2. 위치와 물건의 의미

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 공간 | 탐색을 시작하는 큰 위치 | 침실, 거실, 사무실, 차량 |
| 보관함 | 물건 또는 다른 보관함이 들어가는 위치 | 옷장, 서랍, 박스, 가방, 파우치 |
| 물건 | 위치를 기록하고 찾는 대상 | 충전기, 여권, 리모컨 |

```text
침실
└─ 옷장
   └─ 여행용 파우치
      ├─ 충전기
      └─ 변환 어댑터

거실
└─ TV장
   └─ 리모컨
```

- 구조는 공간 → 보관함 → 보관함 → 물건까지 지원한다. 공간 아래 보관함 중첩은 최대 2단계다.
- 물건은 공간이나 보관함에 바로 등록할 수 있고, 한 번에 하나의 위치만 가진다.
- 다른 물건을 담는 파우치·가방은 보관함으로 등록한다. 보관함 자체도 검색할 수 있다.
- 공간은 최상위 위치이며 보관함은 상위 위치를 가진다. 자기 자신이나 자신의 하위 보관함으로 이동할 수 없다.
- 같은 이름은 허용하고 사진과 전체 위치 경로로 구분한다.
- 물건이나 보관함이 남아 있는 위치는 삭제할 수 없다. 내용물을 먼저 이동·삭제한 뒤 빈 위치를 삭제한다.

## 3. MVP 기능과 제외 범위

| 기능 | 첫 버전의 동작 |
| --- | --- |
| 공간 등록·수정 | 이름 필수, 사진 1장 선택 |
| 보관함 등록·수정 | 이름·상위 위치 필수, 사진 1장 선택 |
| 물건 등록·수정 | 이름·위치 필수, 사진 1장·메모 선택 |
| 위치 탐색 | 공간에서 보관함을 열어 내부 보관함과 물건 조회 |
| 검색 | 공간·보관함·물건 이름, 물건 메모, 현재 위치 경로를 대상으로 검색 |
| 물건 이동 | 목적지를 선택해 현재 위치 변경 |
| 보관함 이동 | 보관함과 내용물의 위치 경로를 함께 변경 |
| 삭제 | 물건 삭제와 비어 있는 위치 삭제 |
| 계정 | 이메일 가입·로그인·비밀번호 재설정·탈퇴 |
| 캐시 조회 | 이미 동기화된 텍스트 데이터 조회·검색 |

사진은 선택 입력이다. 사진을 찍기 어려울 때도 이름과 위치를 먼저 기록할 수 있게 한다. 등록·사진 업로드·이동·삭제 등 변경 작업은 온라인에서 처리하며 완전한 오프라인 편집은 MVP에 포함하지 않는다. 캐시에 없는 데이터나 사진을 오프라인에서 볼 수 있다고 보장하지 않는다.

첫 버전에서는 가족 공유·공동 편집, AI 사진 인식·자동 이름 입력·자연어 해석, QR·바코드·NFC, 수량·가격·구매일·보증 관리, 대여·이동 이력·알림, 물건 일괄 등록·이동, 결제·구독을 제외한다.

## 4. 화면과 핵심 사용자 흐름

| 화면 | 주요 내용 |
| --- | --- |
| 홈 | 검색창, 공간 카드, 공간 추가 |
| 위치 상세 | 현재 경로, 내부 보관함, 바로 들어 있는 물건, 추가 동작 |
| 등록·수정 | 이름, 사진, 위치 선택, 물건 메모 |
| 검색 결과 | 사진, 이름, 전체 위치 경로, 위치 열기 |
| 물건 상세 | 사진, 현재 위치, 메모, 이동·수정·삭제 |
| 설정·계정 | 계정 정보, 비밀번호 재설정, 탈퇴 |

로그인 화면과 위치 선택 화면은 보조 화면으로 둔다. 등록·수정과 이동은 위치 선택 흐름을 재사용한다. 홈에는 공간 카드를 먼저 보여주고, 위치 상세에는 보관함을 먼저, 물건을 아래에 배치한다. 상세 위치의 경로는 눌러 이동할 수 있게 한다.

### 현재 위치에서 등록

1. 사용자가 침실 → 옷장 → 여행용 파우치를 연다.
2. 물건 추가를 누르면 현재 파우치가 위치로 선택되어 있다.
3. 이름과 선택 사진·메모를 입력해 저장한다.
4. 등록된 물건이 현재 위치에 표시된다.

### 단서로 검색

1. `충전기`를 입력하면 해당 물건을 찾는다.
2. 결과에 `침실 › 옷장 › 여행용 파우치` 경로를 표시한다.
3. `여행용 파우치`를 검색하면 보관함과 그 경로 아래의 물건을 찾을 수 있다.
4. 결과에서 물건 상세 또는 해당 위치를 연다.

`파우치 충전기`처럼 여러 단어를 입력하면 이름·메모·현재 경로를 합친 검색 대상에 모든 단어가 포함된 결과를 찾는 방식으로 설계한다. 띄어쓰기·대소문자·한글 정규화와 결과 정렬은 구현 전 결정한다. “파우치 안에 넣어둔 충전기 찾아줘”처럼 문장의 의미를 해석하는 검색은 제외한다.

### 보관함과 내용물을 함께 이동

1. 여행용 파우치에서 이동을 누른다.
2. 차량을 목적지로 선택한다.
3. 순환 관계와 최대 중첩 깊이를 검증한다.
4. 파우치와 내부 물건의 표시 경로가 `차량 › 여행용 파우치`로 바뀐다.

중복 실행, 이동 중 취소, 저장 성공 후 화면 전환 실패의 처리 방식은 관련 Issue에서 정의한다. 물리적으로 옮긴 상태와 기록된 위치가 달라질 수 있으므로 이동 동작을 쉽게 찾을 수 있게 한다.

## 5. 데이터 설계 방향

아래는 구현을 위한 설계안이며 현재 Firestore에 구성된 컬렉션을 의미하지 않는다.

```text
users/{uid}
  locations/{locationId}
  items/{itemId}
```

| 데이터 | 주요 필드안 |
| --- | --- |
| 위치 | name, type, parentId, photoPath, createdAt, updatedAt |
| 물건 | name, locationId, photoPath, memo, createdAt, updatedAt |

- 위치의 type은 공간 또는 보관함을 구분한다. 공간의 parentId는 없고 보관함은 상위 위치 ID를 가진다.
- 물건은 locationId로 직접 상위 위치를 참조한다. 문서 ID는 이름과 독립적으로 유지한다.
- 전체 경로 문자열은 데이터마다 복제하지 않고 상위 위치 관계로 계산한다. 보관함 이름 변경이나 이동으로 내부 물건을 일괄 수정할 필요를 줄인다.
- 텍스트 저장과 사진 업로드는 별개 작업이다. 사진 업로드 실패 후에도 저장된 이름·위치를 유지하고 사진 재시도 상태를 보여주는 방향으로 설계한다.
- 참조 무결성, 사진 연결 상태, 반복 업로드의 중복 방지, 위치 삭제와 이동의 경쟁 조건은 데이터 구현 Issue에서 검증한다.
- 동시 수정 충돌 정책, 시각의 기준과 스키마 버전은 구현 전에 결정한다. Firestore 기본 동작을 제품 정책으로 자동 채택하지 않는다.

## 6. 기술 선택과 현재 상태

| 영역 | 도입 방향 | 저장소 현재 상태 |
| --- | --- | --- |
| 앱 | Flutter | 3.47.5 stable, 카운터 템플릿 |
| 언어 | Dart | 3.13.4, SDK 제약 ^3.13.4 |
| 상태 관리 | Riverpod | 미설치 |
| 화면 이동 | go_router | 미설치 |
| 계정 | Firebase Authentication | 미설치·미구성 |
| 위치·물건 데이터 | Cloud Firestore | 미설치·미구성 |
| 사진 | Cloud Storage for Firebase | 미설치·미구성 |
| 오류 추적 | Firebase Crashlytics | 미설치·미구성 |
| 서버 처리 | 탈퇴 시 데이터·사진 정리 등 필요한 작업에 Cloud Functions | 미구성 |

UI, 상태·사용자 액션, 도메인 규칙, 데이터 접근의 책임을 분리한다. 구체적인 디렉터리와 인터페이스는 첫 기능 Issue에서 정하고 앱 전체를 위한 불필요한 계층을 미리 만들지 않는다. Firebase 관련 의존성은 대체 가능한 경계로 감싼다.

사용자당 물건 1,000개와 위치 100개를 검색·동기화 설계 및 부하 검증의 기준으로 삼는다. 이는 가입 제한이나 강제 저장 한도가 아니다. 작은 텍스트 데이터를 동기화해 앱 안에서 검색하고 사진은 필요할 때 불러오는 방향으로 검토한다. 데이터 수 증가에 따른 읽기 비용과 메모리 사용량은 측정 후 조정한다.

Cloud Storage 사용에는 Blaze 요금제 연결이 필요하다. 무료 이용 가능 구간이 있어도 실제 비용은 리전과 저장·다운로드 사용량에 따라 달라진다. Firebase 프로젝트·리전, 사진 압축 기준과 예산 알림 금액은 별도로 결정한다. [Firebase Storage 요금제 안내](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)

Firestore 캐시는 사진 캐시나 업로드 재시도를 대신하지 않는다. 동기화가 끝나지 않은 결과와 완전한 검색 결과를 구분해 표시한다. [Firestore 오프라인 문서](https://firebase.google.com/docs/firestore/manage-data/enable-offline)

## 7. Android와 iOS 대응

- Android와 iPhone을 첫 주부터 함께 빌드하고 매주 핵심 흐름을 실행한다.
- iOS 기획상 지원 범위는 18.0~27.0이다. 18·26·27.0을 중점 검증하고 중간 지원 버전은 기본 동작을 점검한다.
- Flutter 공식 지원표에는 3.47 기준 iOS 15~27이 포함되어 있으나, 사용하는 Firebase·사진 플러그인 조합과 앱의 실기기 호환성은 별도 검증한다. [Flutter 공식 지원 범위](https://docs.flutter.dev/reference/supported-platforms)
- 현재 Xcode 프로젝트는 iPhone과 iPad 대상 설정을 가지고 있다. MVP는 iPhone 중심이며 iPad 지원 여부와 기기 대상 설정은 플랫폼 Issue에서 정리한다.
- Android 최소 지원 버전은 아직 제품 정책으로 확정하지 않았다. 현재 minSdk와 targetSdk는 Flutter 기본값을 참조한다.
- 작은 화면부터 큰 화면, 안전 영역, 키보드, 글자 확대, 뒤로 가기 제스처, VoiceOver·TalkBack을 확인한다.
- 카메라·사진 선택, 권한 거부와 취소, HEIC·사진 방향·압축, 앱 복귀 후 업로드 상태와 재시도를 실기기에서 확인한다.
- 첫 주의 기술 검증은 로그인 → 사진 선택·촬영 → 압축 → Firebase 업로드 → 저장 데이터 재조회다. 검증한 SDK·플러그인 조합을 기준으로 개발한다.
- iOS 앱 서명·TestFlight·App Store, Android 배포 서명·베타·스토어 제출을 출시 작업에 포함한다. 현재 Android release 설정은 debug 서명을 사용하므로 출시 준비 완료 상태가 아니다.
- iOS 빌드에는 Mac과 Xcode가 필요하다. 실제 설치된 도구와 iOS 27.0 테스트 기기를 확인하며 시뮬레이터 빌드만으로 실기기 검증 완료를 선언하지 않는다. [Flutter iOS 배포 안내](https://docs.flutter.dev/deployment/ios)

## 8. 상태와 보안의 제품 기준

- 공간·보관함·검색 결과의 빈 상태에서 추가 또는 검색 수정 행동을 안내한다.
- 등록·이동·삭제·사진 업로드는 진행 중, 완료, 실패와 재시도를 구분한다. 온라인 변경이 불가능한 상황에서는 저장 완료로 표시하지 않는다.
- 다른 사용자의 텍스트와 사진에 접근할 수 없도록 인증·소유권을 검증한다. 접근 규칙은 기본 거부에서 필요한 범위만 허용한다.
- 로그에 물건 이름·메모·사진·위치 경로·인증 정보를 남기지 않는다.
- 탈퇴 시 계정뿐 아니라 사용자 데이터와 사진도 정리한다. 재인증, 정리 순서, 부분 실패·재시도와 보관 기간은 구현 전 결정한다.

## 9. 구현 순서와 예상 일정

Flutter 경험이 있고 주 20~25시간 투입한다는 가정에서 10~14주를 예상한다. 일정은 구현·검증을 위한 추정이며 스토어 심사 완료일을 보장하지 않는다.

| 기간 | 작업 | 단계 완료 기준 |
| --- | --- | --- |
| 1주차 | 양쪽 플랫폼, iOS 27.0 사진·Firebase 연결 검증 | 실제 사용할 조합에서 사진 저장·재조회 확인 |
| 2~4주차 | 공간·보관함·물건 등록과 위치 탐색 | 사진 없이 등록·탐색·재실행 후 조회 |
| 5~6주차 | 사진 처리, 검색, 물건·보관함 이동 | 실패 재시도와 이동 후 전체 경로 확인 |
| 7~8주차 | 계정, 접근 규칙, 탈퇴, 오류 처리 | 타 계정 접근 차단과 데이터·사진 정리 확인 |
| 9~10주차 | 양쪽 실기기, 버전·화면 크기 검증 | 지원 범위의 핵심 흐름과 접근성 점검 |
| 11~14주차 | TestFlight·Android 베타, 피드백, 스토어 제출 | 주요 오류 해결과 배포 준비 |

기능을 늘리기보다 등록 → 찾기 → 이동을 먼저 완성한다. 각 단계의 변경은 Issue와 PR로 나누고 기획 수치를 실측 결과처럼 보고하지 않는다.

## 10. 출시와 사용자 검증 기준

- Android와 iOS 27.0 실기기에서 등록 → 검색 → 물건·보관함 이동 → 재실행 후 위치 확인이 동작해야 한다.
- 위치 이름 변경과 보관함 이동 후 내부 물건의 탐색·검색 경로가 일치해야 한다.
- 순환 이동, 깊이 초과 이동과 비어 있지 않은 위치 삭제를 막아야 한다.
- 사진 선택 취소·권한 거부·업로드 실패 후에도 기존 데이터가 손상되지 않아야 한다.
- 캐시 조회의 범위와 온라인 변경 제한이 실제 화면과 일치해야 한다.
- 계정 간 데이터 접근 차단과 탈퇴 정리의 완료 조건을 충족해야 한다.
- 관련 테스트, 분석과 플랫폼 빌드가 통과하고 기기 검증 및 수행하지 못한 검증을 PR에 기록해야 한다.

사용자 5~10명에게 물건 20개씩 등록하도록 요청해 사용성을 확인한다. 현재 위치에서 물건 등록 30초 이내, 며칠 뒤 단서로 위치 확인 10초 이내를 목표로 관찰한다. 이는 검증용 목표이며 달성한 성능 수치가 아니다. 실제 이동 후 앱에서도 위치를 수정하는지, 보관함 이동의 결과를 이해하는지도 확인한다.

## 11. 구현 전 결정할 사항

미결정 사항은 관련 Issue에서 선택지와 영향을 제시해 확인한다. 이 표는 필요한 결정을 드러내기 위한 것이며 제시된 선택지를 확정 정책으로 해석하지 않는다.

| 결정할 내용 | 검토할 선택지와 영향 |
| --- | --- |
| Firebase 프로젝트·리전·예산 | 사용자 위치, 지연, 비용, 운영 환경 분리와 예산 알림 기준 |
| Android 최소 지원 버전·iPad 대상 | 지원 기기 범위와 테스트·플러그인 제약 |
| 사진 크기·품질·형식·삭제 정책 | 업로드·저장 비용과 식별 가능한 사진 품질, 실패한 파일 정리 |
| 입력 길이·검증·등록 취소 | 허용 길이, 공백 처리, 미저장 입력의 이탈 확인 |
| 검색 정규화·결과 정렬 | 공백·대소문자·한글 처리, 같은 이름의 결과 우선순위 |
| 동시 수정·이동 충돌 | 최신 변경 우선 또는 충돌 확인, 삭제와 이동의 경쟁 처리 |
| 사진 재시도와 앱 종료 | 명시적 수동 재시도 또는 지속 작업 큐, 재실행 후 복구 범위 |
| 계정 탈퇴·보관 기간 | 재인증, 즉시 정리 또는 유예, 실패 재시도와 삭제 완료 확인 |
| 디자인 시스템·패키지 버전·구조 | 공통 토큰, 책임별 구성, 실제 양쪽 플랫폼에서 검증한 의존성 |

위 사항이 해당 기능의 결과에 영향을 주면 먼저 결정하고 구현한다. 다른 독립 기능이나 읽기 전용 조사는 계속 진행할 수 있다.
